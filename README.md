# Millex Market

Интернет-магазин цифровых товаров: React/Vite интерфейс, FastAPI API, PostgreSQL и Redis.

## Что реализовано

- Каталог игр и товаров, страница аккаунтов, личный кабинет и админ-разделы.
- В редакторе читов администратор может вручную создавать категории и назначать для каждого чита списки функций через запятую; на странице чита категории раскрываются под описанием товара.
- В редакторе чита можно собирать галерею из скриншотов и видео по URL, загружать видео до 500 МБ прямо с компьютера порциями по 512 КиБ, задавать подписи и менять порядок; на странице товара работает карусель с переключением по миниатюрам и автозапуском видео с контролами. Поддерживаются YouTube, Vimeo и прямые MP4/WebM/OGG-ссылки.
- Администратор может загружать фон карточки Telegram на главной; каталог `/uploads/` общий для backend и Docker-хоста. Production nginx напрямую раздаёт видео из постоянного `/var/lib/millex/uploads/videos/` как по `/uploads/videos/<file>`, так и по совместимому URL `/uploads/<file>`, с поддержкой HTTP Range; остальные файлы проксируются в backend.
- Оформление заказа через Platega и покупка с баланса; выдача товара зависит от типа позиции и наличия ключей/оператора.
- При покупке чита через Platega, в том числе без регистрации, подтверждённый webhook резервирует свободный ключ и завершает заказ. Фоновый email-worker сервиса `millex-bot` отправляет ключ на адрес, введённый при гостевой покупке; для доставки должны работать сервис `bot`, SMTP-настройки и быть свободный ключ для alias товара.
- Накопительная скидка хранится у пользователя в `users.discount_percent`: при успешной оплате растёт на 1% до 10%. Скидка применяется к последующим заказам.
- Общая акция −20% на покупки через сайт и Telegram WebApp действует до 14 ноября 2026 года включительно. Акция заменяет, а не суммирует накопительную скидку.
- В разделе бухгалтерии администратор видит проводки пополнений и покупок читов через каталог, задаёт комиссию и себестоимость тарифов, добавляет расходы; прибыль не рассчитывается для продаж без заданной себестоимости.
- Адаптивная мобильная шапка и страницы; выход пользователя доступен из мобильного меню.

## Запуск для разработки

- Frontend: `cd frontend`, `npm ci`, `npm run dev`; production-сборка — `npm run build`. Production-сборка удаляет вызовы `console.*` и `debugger`; в режиме разработки диагностика остаётся доступна.
- Backend и инфраструктура: настройте переменные окружения backend и запустите `docker compose up --build`.
- API health endpoint: `/api/health`.
- Чтобы создать отсутствующие таблицы по текущим backend-моделям и пустые legacy-таблицы каталога `items`/`categories`, выполните `docker compose exec backend python -m app.create_schema` из корня проекта. Скрипт идемпотентен: не удаляет таблицы и данные, добавляет отсутствующие legacy-колонки, но не импортирует данные из дампа. Для production сначала сохраните резервную копию базы.
- Чтобы создать или дополнить legacy-таблицу аккаунтов, выполните `docker compose exec backend python -m app.create_accounts_table`. Скрипт идемпотентен, не удаляет строки и создаёт колонки по старой структуре `accounts`. В исходном `millex.sql` эта таблица пустая, поэтому создание схемы исправит ошибку API, но не добавит аккаунты в каталог.
- Перенос единственного исходного MySQL-дампа запускается через временный профильный сервис `legacy-db`: `docker compose --profile legacy-import up -d legacy-db`, копирование `/root/millex.sql` в контейнер и импорт через `mysql`, затем `docker compose exec backend python -m app.migrate_legacy` для dry-run и `docker compose exec backend python -m app.migrate_legacy --apply` после проверки. `psql` не может исполнить исходный MySQL-дамп; отдельный PostgreSQL-дамп не нужен. Скрипт сохраняет строки всех исходных таблиц в `legacy_archive.rows` (JSONB), адаптирует категории, товары, пользователей и блог к текущей схеме, а остальные таблицы оставляет в архиве. Существующие целевые строки не перезаписываются. Пользователи импортируются без прав администратора; администраторов нужно назначить отдельно. Хеши паролей, не поддерживаемые текущим backend, потребуют сброса пароля.
- Перед переносом сохраните копию целевой БД и загрузок. Добавьте `LEGACY_MYSQL_PASSWORD` в корневой `.env` и передайте обновлённый Compose/код на сервер. Из `~/millex` запустите `docker compose --profile legacy-import up -d legacy-db`, затем `docker compose cp /root/millex.sql legacy-db:/tmp/millex.sql` и `docker compose exec -T legacy-db sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < /tmp/millex.sql'`. После пересоздания backend (`docker compose up -d --build backend`) выполните dry-run и проверьте числа строк; добавляйте `--apply` только после проверки. Импорт исходника производится в отдельный MySQL-контейнер/volume `legacy_mysql_data`, рабочий PostgreSQL volume не очищается. Архив содержит исходные пользовательские данные и хеши паролей — ограничьте доступ к production-БД и резервным копиям.
- Подробная инструкция по production-резервированию и восстановлению: [BACKUP_RESTORE.md](./BACKUP_RESTORE.md).
- Минимальная сумма пополнения баланса через Platega — 50 ₽; это значение проверяется API и показывается во всех пользовательских формах пополнения.
- Callback Platega: `https://millex.market/api/payments/webhook`. Backend проверяет `X-MerchantId`/`X-Secret`, сверяет сумму и валюту подтверждённой оплаты, связывает callback с сохранённой заявкой пополнения и зачисляет баланс однократно. Комиссия способов оплаты по настройкам Platega удерживается с покупателя, поэтому сохраняются отдельно сумма пополнения к зачислению и ожидаемая сумма платежа с комиссией; покупательская надбавка не зачисляется на баланс. Для SBP QR, карточного эквайринга и криптовалюты заданы ставки 5%, 6% и 2%. При возврате пользователя на страницу баланса backend дополнительно проверяет ожидающую транзакцию через официальный Platega `GET /transaction/{id}`; только `CONFIRMED` с совпадающими ID, суммой и валютой зачисляет средства. Для ручной проверки используйте тестовое пополнение и запрос статуса из backend/Platega API, не отправляйте вручную поддельный callback `CONFIRMED`.
- Таблицы бухгалтерии создаются при старте backend, а отсутствующие поля `accounting_*` в `bot_orders` добавляются идемпотентной миграцией. Перед первым production-деплоем сделайте резервную копию БД. Новые проводки включают только пополнения Platega и покупки читов через `/api/payments/buy`; исторические операции и заказы другого потока (`orders`) автоматически не импортируются.

## Клиентский Telegram-бот

Клиентский бот запускается отдельным Compose-сервисом `client-bot` и не использует админский бот `millex-bot`. На `/start` он отвечает кнопкой «Открыть MILLEX», которая открывает Mini App.

Создайте нового бота через BotFather и задайте его токен в корневом `.env`:

```env
CLIENT_BOT_TOKEN=<токен нового клиентского бота>
CLIENT_MINI_APP_URL=https://millex.market
```

Затем запустите сервис командой `docker compose up -d --build client-bot`. Не добавляйте токен в Git или исходный код. Если токен ранее отправлялся в переписке, отзовите его через BotFather и используйте новый.

В production Docker Compose монтирует `/var/lib/millex/uploads` на сервере в `/app/uploads` backend-контейнера; backend сохраняет собранные видео в `/app/uploads/videos`, то есть напрямую в `/var/lib/millex/uploads/videos` на хосте. В админке ссылка берётся из ответа backend и формируется как `https://millex.market/uploads/videos/<имя-файла>`. Старые адреса `/uploads/<имя-файла>.mp4` тоже направляются в эту же папку. `millex.market.nginx.conf` раздаёт видео напрямую через nginx, чтобы браузер мог запрашивать диапазоны байтов и перематывать видео; отсутствующие файлы возвращают 404, а не SPA HTML. Не храните файлы в папке frontend, которую заменяют при деплое. При изменении volume пересоздайте backend-контейнер и перезагрузите nginx.

При запуске backend добавляет JSONB-колонку `items.gallery`, если legacy-таблица `items` существует, и переносит текущие `preview`/`video` в неё только для ещё не инициализированных галерей.

## SEO

- В `/admin/seo` редактируются общие SEO-настройки, H1 и HTML-текстовый блок фиксированных публичных страниц. В редакторах статей, игр и товаров доступны индивидуальные title, description, H1, SEO-текст, изображение для превью и `noindex`; текстовые блоки очищаются от небезопасного HTML перед показом, а пустые поля используют значения по умолчанию.
- SEO-тексты каталога и страниц игр выводятся в доступном сворачиваемом блоке «Описание»; содержимое доступно посетителям по раскрытию, а текстовые элементы принудительно используют контрастный цвет поверх legacy CSS.
- Для переноса SEO-метаданных из старого MySQL dump используйте `python -m app.services.legacy_seo_import --dump "путь/к/millex.sql"` из каталога `backend`. На сервере с Docker Compose можно передать dump через stdin: `docker compose exec -T backend python -m app.services.legacy_seo_import --dump /dev/stdin < /путь/к/millex.sql` (запускайте из каталога проекта). Импортёр подключается к БД из `backend/.env`, создаёт недостающие SEO-колонки, сопоставляет фиксированные страницы, категории, товары и статьи и заполняет только пустые поля. Перед запуском проверьте конфигурацию БД и сделайте резервную копию.
- Основные страницы задают отдельные title, description, canonical URL, Open Graph/Twitter metadata и JSON-LD. Личные, платёжные и служебные страницы помечаются `noindex`.
- `frontend/public/robots.txt` указывает на `https://millex.market/sitemap.xml`. В production этот URL проксируется nginx из `millex.conf` в backend: карта сайта формируется по индексируемым публичным страницам, играм, активным товарам и видимым статьям; сущности с `noindex` из неё исключаются.
- После изменения nginx-конфигурации установите её на сервере и перезагрузите nginx; после изменений frontend соберите и опубликуйте содержимое `frontend/dist`, а backend пересоберите/перезапустите. Статический `frontend/public/sitemap.xml` — только fallback для основных страниц; актуальный полный sitemap в production отдаёт backend.
- Метаданные отдельных React-страниц обновляются при запуске JavaScript. Google может индексировать отрендеренный SPA, но некоторые социальные превью-боты читают только исходный HTML; для гарантированных отдельных превью на каждой динамической странице потребуется SSR или prerender.

## Реферальная программа

- В личном кабинете `/profile/referrals` пользователь получает уникальную ссылку вида `/register?ref=...`; код приглашения сохраняется при регистрации.
- После успешной оплаты покупки приглашённого 5% от её суммы зачисляются на баланс пригласившего. Повторные уведомления об оплате не дублируют начисление, а при chargeback комиссия сторнируется.

Для Compose задайте `POSTGRES_PASSWORD` в корневом `.env` (не коммитьте его); при необходимости также `POSTGRES_USER` и `POSTGRES_DB`. В `backend/.env` задайте `SECRET_KEY`, `DATABASE_URL`, `PLATEGA_MERCHANT_ID`, `PLATEGA_SECRET` и для выдачи аккаунтов `NFA_API_KEY` или `NFA_TOKEN`. `DATABASE_URL` должен подключаться к хосту `db` (например, `postgresql://millex:<пароль>@db:5432/millex`) и использовать те же имя пользователя, пароль и базу, что PostgreSQL в Compose. В backend `REDIS_URL` задаётся Compose как `redis://redis:6379/0`. Не добавляйте `.env` с реальными значениями в Git.

## Оплата и пополнение баланса

- В Platega укажите callback `https://millex.market/api/payments/webhook`. Для возврата пользователя используется `SITE_URL`; production Compose задаёт `https://millex.market`, а backend default тоже больше не использует dev-порт `5173`.
- `PLATEGA_MERCHANT_ID` и `PLATEGA_SECRET` — отдельные обязательные значения из кабинета провайдера; backend больше не использует Merchant ID как fallback для секрета.
- Пополнение записывается в `balance_topups` до обращения к провайдеру и связывается с ним уникальным reference и transaction ID. Callback может найти его по transaction ID или reference в payload; для `CONFIRMED` обязательны сумма и валюта, которые сверяются с заявкой. Повторные уведомления не зачисляют средства повторно. На возврате в личный кабинет статус конкретного пополнения опрашивается по reference и после подтверждения обновляется профиль.
- После обновления backend новая таблица и недостающие колонки/индексы создаются при старте. Перед production-деплоем сделайте резервную копию БД. Исторические оплаты, для которых Platega уже прекратила повторы callback, нужно сверить и при необходимости зачислить вручную только после подтверждения успешного статуса в кабинете Platega.

## Выдача товара и email

- Аккаунт покупается через NFA Resell API (`POST /api/v1/activate_direct`, тип берётся из alias товара). API возвращает `exe_base64`/`exe_filename`; backend сохраняет файл в заказе. Файл доступен покупателю по авторизованной ссылке из истории заказов; email отправляет уведомление со ссылкой, не прикладывая `.exe`, который почтовые провайдеры часто блокируют. Запрос проксируется только через backend; nginx для `/api/accounts/` настроен на таймаут 240 секунд.
- Для каталога сначала резервируется свободный ключ из таблицы `keys` по `item_alias`, равному slug товара. Если ключей недостаточно, платёж не теряется: заказ попадает в очередь Telegram-бота для ручной выдачи; после выдачи бот обновляет заказ, и email worker отправляет ключи покупателю.
- Оплаченный заказ чита со свободным ключом автоматически завершается и показывает ключ на странице доставки; покупка с баланса тоже резервирует ключ. Без свободного ключа сохраняется очередь ручной выдачи. Ключи можно загрузить в `/admin/products`: нажмите «Ключи» у товара и загрузите `.txt` или вставьте список (один ключ на строку, максимум 5000 за запрос); повторные значения пропускаются.
- При создании заявки на пополнение баланса админский Telegram-бот уведомляет администраторов о сумме, email и нике пользователя; после подтверждения платежа отправляется отдельное уведомление о фактическом зачислении.
- При создании оплаты Platega для покупки гостем без аккаунта админский Telegram-бот присылает заказ, товар, сумму и email; после подтверждения оплаты остаётся отдельное уведомление о продаже.
- Письма отправляет фоновый worker Telegram-бота. Ошибки сохраняются на заказе, повторы выполняются с растущей задержкой до часа, одна ошибочная доставка не блокирует очередь; после исправления SMTP отправка автоматически повторится. Покупка аккаунта не зависит от доступности SMTP: файл сохраняется в заказе, доступен для скачивания после входа, а письмо служит дополнительным уведомлением. Для остальных покупок email по-прежнему необходим, так как ключи доставляются по email.

Для выдачи аккаунтов задайте `NFA_API_KEY` в `backend/.env` на сервере (рядом с `backend` Dockerfile/Compose env_file). Ключ создаётся в NFA bot: `/start` → Panel → API → Create API key; API использует его в заголовке `X-API-Key`. Не путайте его с API-ключом NotiSender или SMTP-паролем. После изменения `.env` пересоздайте backend-контейнер. Документация: https://nfa-api.acode.ing/docs. Backend вызывает `POST /api/v1/activate_direct` с `account_type`, взятым из `accounts.alias`, и сохраняет `exe_base64` в заказе. Проверьте, что `accounts.alias` точно совпадает с типом аккаунта, доступным в NFA. Время ожидания активации ограничено 140 секундами; nginx для `/api/accounts/` настроен на таймаут 240 секунд. Если ключ отсутствует, endpoint теперь возвращает `503` с указанием настройки; если NFA отклоняет ключ — ответ сообщает, что нужно проверить `NFA_API_KEY`.

Для SMTP задайте в корневом `.env` `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_FROM_EMAIL`, `SMTP_USE_TLS` и `SMTP_USE_SSL`. Эти параметры передаются backend и Telegram-боту. Для REG.RU с STARTTLS используйте `SMTP_HOST=mail.hosting.reg.ru`, `SMTP_PORT=587`, полный адрес ящика в `SMTP_USERNAME` и `SMTP_FROM_EMAIL`, пароль этого ящика в `SMTP_PASSWORD`, `SMTP_USE_TLS=true` и `SMTP_USE_SSL=false`. Эти же значения хоста, порта и TLS используются Compose по умолчанию; учётные данные нужно задать в корневом `.env`. Для Compose задайте `POSTGRES_PASSWORD`; он должен совпадать с паролем в `DATABASE_URL` backend и бота. В `millex-bot/.env` нужны `BOT_TOKEN`, `BOT_ADMIN_IDS` и `DATABASE_URL` с драйвером `postgresql+asyncpg` и hostname `db`.

Если серверу нужен прокси для Telegram Bot API, задайте в корневом `.env` `TELEGRAM_PROXY_URL`: `http://username:password@proxy-host:proxy-port` для HTTP(S) или `socks5://username:password@proxy-host:proxy-port` для SOCKS5. Compose передаст его обоим ботам (`bot` и `client-bot`). Убедитесь у провайдера, что endpoint поддерживает указанный протокол. Код и Git не должны содержать реальные данные доступа; экранируйте специальные символы логина/пароля в URL. После настройки пересоздайте оба контейнера.

Транзакционные письма — восстановление пароля и доставка купленных ключей/файлов — отправляются через SMTP. Для почтового ящика REG.RU используйте указанные выше настройки STARTTLS и пароль ящика (не пароль от панели управления). Для альтернативного SSL-соединения установите порт 465, `SMTP_USE_TLS=false` и `SMTP_USE_SSL=true`. Пароли пользователей сайта письмами не отправляются.

### Unisender Go для массовых рассылок

- Раздел `/admin/emailer` отправляет массовые кампании через Unisender Go Web API. Этот канал не используется для восстановления пароля и доставки заказа.
- Для кампаний подтвердите домен/адрес отправителя и настройте SPF, DKIM и DMARC в Unisender Go. API-ключ задайте как `UNISENDER_GO_API_KEY` в `backend/.env`; при необходимости укажите `UNISENDER_GO_API_URL` (по умолчанию `https://goapi.unisender.ru/ru/transactional/api/v1`). Не сохраняйте API-ключ в Git.
- В админке email-рассылок отображаются состояние API и число адресов пользователей.
- При создании кампании можно выбрать всех пользователей, найти одного или нескольких аккаунтов по email/нику либо указать один адрес для теста. Для выбранных аккаунтов email сохраняется снимком в черновике, поэтому изменение адреса в профиле после создания кампании не меняет аудиторию.
- Кампания без тестового адреса и выбранного списка получателей включает все непустые адреса пользователей, в том числе неактивных. Дубликаты исключаются. API принимает до 500 получателей за запрос; кампания на 20 000 адресов разбивается на 40 запросов. Адреса отписавшихся/некорректные адреса обрабатываются Unisender Go; обход отписок отключён.
- Отправка выполняется фоновым заданием backend-контейнера, счётчики сохраняются в БД после каждого пакета. Не перезапускайте backend до завершения кампании. Статус «Отправлено» означает, что провайдер принял запросы, но не гарантирует доставку во входящие.

Пользователь может восстановить пароль через `/forgot-password`. Backend отправляет через SMTP одноразовую ссылку; она действует 30 минут, повторный запрос для одного аккаунта ограничен интервалом в минуту. Форма явно сообщает, если email отсутствует в БД; это позволяет проверять зарегистрированные адреса. Токен ссылки удаляется из адресной строки до загрузки аналитики; аналитика и чат поддержки отключены на странице сброса пароля.

Фон карточки Telegram редактируется в `/admin/homepage`. Допустимые форматы — PNG, JPEG и WebP, максимальный размер — 5 МБ. Backend сохраняет файлы в `/app/uploads/homepage` внутри контейнера; production Compose монтирует `/var/lib/millex/uploads` сервера в `/app/uploads`. Запросы `/uploads/`, кроме `/uploads/videos/`, проксируются nginx в backend. Для сохранения файлов при деплое оставляйте host-каталог неизменным.

## Перед запуском реальных продаж

Production-платежи и SMTP-доставка не проверялись с реальными аккаунтами провайдера. До запуска замените ранее раскрытые ключи Platega и настройте новые через окружение; проведите полный тест успешных/неуспешных платежей, повторных webhook, выдачи ключа со склада, пустого склада/Telegram fallback, NFA-выдачи `.exe`, письма и повторной отправки после сбоя SMTP. Проверьте, что `millex.conf` установлен в nginx и применён. В `backend/alembic/versions` пока нет миграций: изменения схемы добавляются idempotent `ALTER TABLE` при старте backend, но существующую production-БД следует предварительно резервировать и проверять отдельно. Также настройте резервные копии, мониторинг, TLS и процедуру возвратов/chargeback.
